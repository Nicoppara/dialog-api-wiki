如果只想向玩家显示一条通知，Paper 和 DialogAPI 都能完成。选择 DialogAPI 的理由通常出现在第二步：玩家已经退出或换了页，刚跑完的查询还该不该显示？在 DialogAPI 中，受管页面会记录这次操作属于谁、属于哪一页，插件可以专注于查询和展示结果。

## 🧩 原版能显示什么

| 能力 | Paper 26.3 与 DialogAPI 1.2.0 的覆盖 |
| --- | --- |
| 5 种页面 | 通知、确认、多按钮、页面列表、服务器链接 |
| 2 种正文 | 富文本，以及带可选说明、尺寸与提示的物品 |
| 4 种输入 | 单行或多行文本、复选框、单选、数值滑块 |
| 页面行为 | 外部入口标题、Esc、暂停、点击后关闭、保留原页或进入等待屏幕 |
| 按钮动作 | 静态点击事件（含打开另一页）、代入输入值的命令模板、携带 NBT 的自定义点击 |
| 展示与注册 | 游戏与登录配置阶段的展示和关闭、访问内置页面、启动时注册自定义页面 |

这张表按原版客户端能表达的行为核对。Paper 还提供自己的构建器操作，例如用 `RegistryBuilderFactory.copyFrom(key)` 从注册项起草新页面。DialogAPI 1.2.0 的 `PreparedDialog.registered(key)` 用于**展示**已有注册项，库里没有对应的复制编辑入口。[Paper 官方 Dialog 指南](https://docs.papermc.io/paper/dev/dialogs/) · [DialogAPI 原生页面与注册](native-dialog.md)

## 🔀 哪些工作可以交给库

| 场景 | 直接使用 Paper | 使用 DialogAPI |
| --- | --- | --- |
| 玩家连点提交，或换页后旧点击才抵达 | 回调支持次数和有效期。插件维护动作属于哪个玩家、哪一页 | `showNativeFrame` 为当前玩家的当前帧绑定动作，换页后旧键失效 |
| 玩家连续搜索并在途中退出 | 插件安排后台任务，自行合并请求、丢弃过期结果 | `afterRead` 同一玩家保留一个执行中的读取和最新待处理请求；配合受管退出动作，只发布仍有效的结果 |
| 玩家发回单选值或滑块值 | `DialogResponseView` 提供按类型取值的方法，插件按表单约束检查结果 | 受管表单按本页声明检查字段、选项 ID 和数值范围；业务权限与扣费由插件检查 |
| 多人看同一张静态页 | 可以复用已构建的 Paper Dialog；后台准备和线程交接由插件组织 | 可以复用 `PreparedDialog`。`compileAsync` 先复制物品、解析注册引用，再在指定执行器构建 |
| 一个已注册列表里，注册键排在内联页前面 | build 41 的原生列表反向转换会把后续内联项当作注册引用，导致转换失败 | 注册适配逐项保留引用或内联内容；隔离服验证了混排顺序和前向引用 |

最后一项对应 build 41 的一条具体转换路径。其他几项都可以由 Paper 插件自行编写。两者使用同一个原版客户端，玩家在原生等待屏幕本地退出时，服务端都收不到上一张表单的退出动作。可取消查询的写法见[按钮与退出](actions.md)。

## 🧵 Paper 原生 Dialog 可以在 Folia 使用吗？

可以。在游戏阶段，插件可以在目标玩家所属的区域调用 `player.showDialog(dialog)` 和 `player.closeDialog()`。若从后台查询或另一名玩家的区域发起操作，插件负责把任务交给目标玩家的实体调度器。登录配置阶段使用对应的配置连接，此时尚无游戏内玩家实体。[Paper 原生 Dialog 指南](https://docs.papermc.io/paper/dev/dialogs/) · [PaperMC 的 Folia 调度说明](https://docs.papermc.io/paper/dev/folia-support/)

在官方 Folia 26.3 build 26 的隔离服上，仅用 Paper 的 `Dialog.create` 和 `DialogBody.item` 生成含三颗钻石的表单。协议客户端两次收到展示包并提交文本和复选框，分别触发了固定动作键的 `PlayerCustomClickEvent` 和 Paper 自带的点击回调，两次都收到了关闭包。展示、事件、回调和关闭时都记录到线程拥有目标玩家。

DialogAPI 1.2.1 把线程交接放进受管入口。例如，`runtime.showPrepared(player, page)` 会按目标玩家调度，`afterRead` 会在回到该玩家后检查结果是否仍属于当前页面。直接调用 `page.show(player)` 时，调用方负责线程归属。[接入与双区域验证](async.md)

## ⏱️ 同一张表单，构建要多久

在下列测量中，**从同一份表单构建一次，耗时由 13.766 μs 降至 1.167 μs，每次线程分配减少约 91%**。也就是在这个场景中，原路径的构建耗时约为新路径的 **11.8 倍**。

| 服务端构建路径 | 每次构建耗时中位数 | 每次线程分配中位数 |
| --- | ---: | ---: |
| Paper builder，从相同的 `DialogFrame` 构建 | 13.766 μs | 53,664 B |
| DialogAPI，从相同的 `DialogFrame` 构建 | 1.167 μs | 4,864 B |
| DialogAPI，提前备好 `NativeDialog` 定义后再构建 | 0.553 μs | 2,408 B |

前两行的起点相同。第三行已经提前转换好了定义，计时区间仍包含生成原生页面对象。对于长期复用的静态页，两个库都可以只构建一次，后续展示无需重复支付表中的成本。

**测量方法。** Windows 11、HotSpot Java 25.0.3、Paper 26.3 build 41，堆为 512 MiB–1 GiB。样本含文字、一件附说明的物品、四种输入、两个操作按钮和一个退出按钮。先核对游戏阶段的数据包体逐字节相同，再在服务端线程上为每条路径预热 80,000 次，轮换顺序测七批，每批每条路径构建 40,000 次。分配量来自 HotSpot 的线程分配计数器。最后两批受主机负载影响，表中保留全部批次取中位数。网络、数据库、客户端绘制和整服 TPS 均在计时区间之外。[下载七批原始测量 CSV](https://nicoppara.github.io/dialog-api-wiki/benchmarks/paper-26.3-41.csv)

## 💎 重复打开同一张物品说明页

DialogAPI 1.2.1 在 Paper 26.3 build 41 上分别构建了一张钻石说明页和一张钻石剑说明页。每张都只有一个物品正文。剑带有自定义名称、两行说明、附魔、耐久、模型和插件自定义数据。

| 同一份内联物品页 | 每次构建并编码 | 编译一次，后续仅编码 | 每次编码的包体 |
| --- | ---: | ---: | ---: |
| 普通钻石 | 7.962 μs | 6.926 μs | 273 B |
| 带组件的钻石剑 | 17.058 μs | 14.263 μs | 612 B |

两条路径生成的包体逐字节相同。复用时，每次线程分配分别从 9,752 B 降到 7,704 B、从 16,672 B 降到 14,608 B。表中取七批中位数，每批每条路径测 18,000 次，使用同一游戏协议编码器和可复用的缓冲区。两条路径的批次耗时有重叠。计时到写完包体为止，未计网络、客户端绘制或玩家看到页面的延迟。[下载页面和物品模板的原始测量 CSV](https://nicoppara.github.io/dialog-api-wiki/benchmarks/dialog-item-1.2.1-paper-26.3-41.csv)

另测了从底层物品直接取得模板，比较当前实现 `CraftItemStack.asTemplate`。两种写法在普通物品上每次均分配 24 B，在带组件的剑上均为 40 B。耗时区间有明显重叠，1.2.1 继续使用现有物品快照实现。

**高频固定页还可以按注册键发送。** 把上面两张相同的物品页注册到服务端，完成注册表同步后再显示。在这次测试使用的注册表编号下，游戏阶段的展示包体从 **273 B、612 B 都降到 1 B**，这个字节表示注册表编号。编号更大时会占用更多字节。该结果只计本次展示的包体，首次同步注册表另有成本。直接使用 Paper 和 DialogAPI 都可以展示注册页。适合所有人看到相同内容的常用物品图鉴；带玩家背包数据或当次会话按钮的页面继续按玩家构建。[如何注册页面](native-dialog.md)

## 🔎 验证到了哪里

Paper 26.3 build 41 隔离服上的协议客户端分别在登录配置阶段和游戏阶段接收展示与关闭包，并把点击经 TCP 送回服务器。回调确认了连接归属，读到了文本、布尔、单选 ID 和滑块值。异步快照另做了交错验证：提交构建后把物品数量从 3 改成 9，工作线程生成的页仍保留 3。

DialogAPI 1.2.0 的 28 项库测试通过；消费插件 FirTown 的构建报告共 2719 项通过，覆盖集成项目的各个模块。游戏客户端画面和其他 Paper 版本需要分别验收。实现如何拆分见[接口与边界](reference.md)。
